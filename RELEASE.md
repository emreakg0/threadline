2. Reserve the final hostname, preferably an owned custom domain. Set `APP_ORIGIN` to its exact `https://<host>` origin with no path, query or fragment. Use one public web port mapped to Express, with `PORT=8080` or the platform-assigned equivalent. Express binds to `0.0.0.0` and serves the SPA, `/demo`, `/privacy`, `/terms` and the same-origin `/api/*`. Confirm the root base path in the built HTML. Use the deployment URL for tests. [Replit custom domains](https://docs.replit.com/features/publishing/custom-domains)
3. Provision a dedicated empty production PostgreSQL database reachable from Replit. Set `DATABASE_URL` in **Deployment secrets** and confirm the connection identity and TLS verification according to the provider. Use least-privilege runtime access and a trusted migration role. Set up encrypted backups with restricted operators, define retention and recovery targets, then restore a test backup into an isolated environment. Keep development data, OAuth state, sessions and beta grants out of production. Replit's schema publishing can omit triggers/functions that Threadline needs. Apply the repository SQL migrations to an empty target and avoid copying or syncing the development schema and data. [Replit database environments](https://docs.replit.com/features/data-and-storage/development-and-production) · [Data recovery](https://docs.replit.com/features/data-and-storage/data-recovery)
4. Set `NODE_ENV=production` and `THREADLINE_PRODUCTION_AI_APPROVED=false` in the deployment. Leave `BASE_PATH` unset or use `/`. Store `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` as deployment-only values from the client below. Check imported secret names and remove any development/provider credentials from the deployment configuration. Review the upload manifest for local authorization files, credentials, database dumps, Git objects and untracked workspace state. Build inputs are source and dependencies. Keep credential values out of build commands, `VITE_*`, logs and screenshots.
5. Use the build and run commands from `.replit`.

   | Setting | Command |

   | Build | `pnpm install --frozen-lockfile && pnpm build:release` |
   | Migrate | `node lib/db/scripts/migrate.mjs` |

6. Verify HTTP redirects to HTTPS, certificate validity, HSTS at the edge, no API caching, callback query redaction, and edge rate limits for sign-in and API traffic.    ```sh

## Google Auth Platform setup

1. In Google Cloud Console select an approved production project. Under **Google Auth Platform → Branding**, set the Threadline app name, monitored user-support email and developer contact. Add the owned authorized domain, verify ownership as required, and configure `https://<final-host>/`, `/privacy` and `/terms` on that same origin.
2. Under **Audience**, choose **External** for testers outside the organization. Keep the app in **Testing** and add the approved test accounts for acceptance. Google exempts basic sign-in scopes from the Testing user-list restriction. Use the restricted deployment access in step 1 as the acceptance gate and verify access from a non-member browser. Before public sign-in, review audience, branding and publishing requirements with the owner. Use a separate development client for development callbacks. [Google audience rules](https://support.google.com/cloud/answer/15549945)
3. Under **Data Access**, use `openid`, email and profile only. Under **Clients → Create client**, choose **Web application**, set the authorized redirect URI to exactly `https://<final-host>/api/auth/google/callback`, and save. Threadline uses server-side authorization code exchange with PKCE and verified UserInfo. Leave JavaScript origins empty for this flow. Enter the client ID and secret in Replit Deployment secrets.
4. Verify the preflight shows the exact callback URI and `S256`. Treat Google consent, branding, published edge behavior and real sign-in as pending until the final-host tests pass. [Google OAuth web server flow](https://developers.google.com/identity/protocols/oauth2/web-server) · [Google brand verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification)

## Hosted browser acceptance

Use two dedicated Google test accounts in separate clean browser profiles. Run the workspace journey at desktop width and on a mobile browser with touch and a narrow viewport. Use synthetic titles, notes and tasks uniquely marked for each test run. Keep AI off. Record outcomes without OAuth codes, cookies, subject IDs, emails or private content.

### Google OAuth

- [ ] In each profile, start signed out. Click **Sign in with Google**, inspect the redirect host and callback origin, then finish consent. Verify the callback returns to `/`, `/api/auth/me` shows the intended tester, and the workspace survives refresh. Inspect cookie attributes without recording values. `focus_session` must be host-only with `Path=/`, `HttpOnly`, `Secure`, `SameSite=Lax` and a seven-day lifetime. The login-state cookies clear on success.
- [ ] In a fresh signed-out profile, open `/api/auth/google/callback` without parameters. Expect HTTP 400 and no session. Initiate consent and abandon it for over ten minutes, then finish if Google permits. Expect state rejection or an expired attempt and no session. A fresh attempt must work. Use the offline one-time state replay test to verify exact reuse rejection without copying callback credentials into notes or logs.
- [ ] Deny consent from a fresh profile. Expect a retry message and no session. Restart and complete sign-in. If Google returns a redirect or client-configuration error, verify the registered callback and published secret configuration, then start again. No credential changes are needed to exercise denial.
- [ ] Create a Brain Dump and task as account A. In B's separate profile, verify they are absent from lists and city. Open A's synthetic document and revision links in B using the saved fixture IDs and expect 404 on the document/revision APIs. Attempt to create a test task under A's project using B's session and expect 404. Confirm A can still access its own data.
- [ ] With A signed in and a synthetic unsaved draft open, have a database operator expire only A's test session rows in the isolated acceptance database. Trigger a private API request, expect 401 and the expiration prompt with draft text still present. Save a copy of the synthetic draft before authenticating again. Confirm a fresh sign-in works and saved records persist. B must remain signed in.
- [ ] Sign out using the account menu. Verify the session cookie is cleared, `/api/auth/me` returns a null user, private reads return 401, and Back or reload does not restore access. Sign in again and confirm the prior workspace is intact.

### Workspace, 3D City and demo

1. [ ] Open the final URL and sign in. Create **New brain dump** with synthetic text, such as `List the materials for the sample workshop. Ask the facilitator to confirm the room.` Save.
2. [ ] Refresh, reopen the saved dump and compare the title and text. Add a line and save. Open revision history and compare **Revision 1 · Original** with the original text. Confirm the latest contains the added line.
3. [ ] Open the saved dump's plan and use **Add a manual action**. Reload to verify the action persists. Approve and convert it to a task, or create a separate fixture task from **Tasks**. Verify the task persists and AI generation is unavailable.
4. [ ] In **Tasks**, open **3D City** and select the fixture project's neighborhood. Select its building with the pointer or the task picker and confirm the saved title and status. Open the shared editor, then return to **List** and confirm the same task. Check pan, zoom, touch usability, a readable inspector and absence of horizontal overflow. Exercise the list fallback on a browser without WebGL2 and record that result separately from rendering.
5. [ ] In a signed-out tab, open `/demo`. Select **Successful run**, **Restart**, then **Play** or **Step forward** with reduced motion. Confirm all four observed pipeline stages succeed and persistence is recorded. Expect a labeled offline mock-provider example and no private link.
6. [ ] Select **Failure and recovery**, restart and step to the end. Confirm the graph-write rollback and recorded manual recovery choice appear. Confirm the recording reports source preservation. Restart again and confirm the recovery only appears once its event is reached. Keep the demo read-only.
7. [ ] Return to the signed-in tab, refresh and compare the saved original revision again. Sign out, revisit the private deep link and confirm the private APIs reject requests while `/demo`, `/privacy` and `/terms` still load.

Local automated equivalents are `lib/db/scripts/release-smoke.mjs`, `capture-browser.mjs`, `city-browser.mjs` and the API tests. Local OAuth completion uses intercepted responses. The hosted Google flow, real device GPU and host edge controls need live verification.

## Privacy and account operations

- Users can access their own workspace and saved source history. A save makes a new immutable source revision. Archiving retains previous content. Session cookies expire after seven days. Browser self-service export and account deletion are unavailable.
- Approve the responsible operator, monitored support and privacy contact, identity verification and request handling, hosting region, retention periods for active data, expired sessions, logs and encrypted backups, and how deletion is applied again after a restore. Expired session rows can remain in PostgreSQL. Schedule purge and backup operations through the approved platform or operator. Update `/privacy`, `/terms` and the security reporting channel with the approved details before public launch.
- For a verified access request, use a trusted shell with the approved `DATABASE_URL`, a privately supplied `THREADLINE_ACCOUNT_SUBJECT` (the verified `focus_users.id`), and a private directory outside the checkout. Run `node lib/db/scripts/account-data.mjs export /private/path/account.json`. The command writes a new mode-0600 JSON file, includes saved revisions and owner-linked workspace records, and omits session secrets and worker lease tokens. Confirm account scope and deliver through an approved secure channel. Dispose of the export on the approved schedule.
- For an approved account deletion, verify the database and account match, pause ingress and sign-in, disable AI and stop all API/worker replicas after running jobs settle. Remove the subject from any approved AI cohort. Run `node lib/db/scripts/account-data.mjs delete --confirm-delete` with the same private settings. The transaction removes the active account's data, original revisions, derived records, graph/progress and sessions. Verify the account and scoped rows are gone and a different test account is unaffected before resuming. There is no sign-in tombstone. A future sign-in can create an empty account. Rehearse backups, logs, export copies and deleted-data handling separately. Keep AI off during the release procedure since erasing run records also removes that account's app-side quota accounting.
- If separately enabled, Gemini receives the consented revision and app planning instructions. The unpaid service terms permit product improvement and human review of submitted content. Confirm age, region, professional-use and data eligibility. The current terms require paid service for a client made available to users in the EEA, Switzerland or UK. No paid access is approved. Database erasure cannot retract data already sent to Google. [Gemini terms](https://ai.google.dev/gemini-api/terms)
